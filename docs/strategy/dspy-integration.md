# DSPy Integration Architecture

DSPy prompt optimization as a compiler pass in the APXM MLIR pipeline.

## What DSPy Is

DSPy (Stanford NLP) replaces manual prompt engineering with programmatic optimization. Given:

1. A **signature** — declarative input/output spec (`"context, question -> answer"`)
2. **Training examples** — tens to hundreds of labeled input/output pairs
3. A **metric function** — scores output quality (boolean or numeric)
4. An **LLM** — the model being optimized for

DSPy's optimizers automatically discover better prompts:

- **BootstrapFewShot** — Runs the program on training data, keeps traces that pass the metric as few-shot demonstrations. Fast, cheap (~$0.50, ~5 min). Minimum ~10 examples.
- **MIPROv2** — Three-phase: (1) bootstrap demos, (2) propose candidate instructions grounded in program traces, (3) Bayesian search over instruction+demo combinations. Best quality (~$2, ~20 min). Minimum ~10-20 examples.
- **COPRO** — Coordinate ascent over instructions. Instruction-only, no demos.

### What a compiled DSPy program produces

After optimization, DSPy's JSON state contains:

```json
{
  "predict": {
    "signature": {
      "instructions": "Given the context, answer concisely. Focus on the most relevant fact.",
      "fields": [
        {"prefix": "Context:", "description": "${context}"},
        {"prefix": "Answer:", "description": "${answer}"}
      ]
    },
    "demos": [
      {
        "context": "The Eiffel Tower was built in 1889...",
        "answer": "1889"
      }
    ]
  }
}
```

- **`instructions`** — Rewritten by the optimizer (replaces original docstring)
- **`demos`** — Few-shot examples selected/generated by bootstrapping
- **`fields`** — Input/output field prefixes and descriptions

### Real-world results

From a [July 2025 production case study](https://arxiv.org/html/2507.03620v1):

| Use Case | Baseline | After DSPy | Optimizer |
|----------|----------|------------|-----------|
| Routing Agent | 85.7% | 90.5% | MIPROv2 |
| Prompt Evaluator | 46.2% | 76.9% | MIPROv2 |
| Jailbreak Detection | 82.9% | 93.2% | MIPROv2 |

The study also found that extracting optimized instructions out of DSPy's framework into an existing pipeline still yields improvements (90% vs 85.7% baseline), though the DSPy team warns it can degrade vs running inside the framework.

## DSPy as a Compiler Pass

### Core idea

`dspy-optimize` is a regular pass in the MLIR pipeline at every optimization level above O0. It is a **no-op** when no training data is available — just like `dead-context-elimination` is a no-op when there's no dead context, or PGO passes are no-ops without profile data.

```
apxm compile flow.apxm -O1   # dspy-optimize in pipeline, no-op if no training data
apxm compile flow.apxm -O2   # dspy-optimize in pipeline, no-op if no training data
apxm compile flow.apxm -O3   # dspy-optimize in pipeline, no-op if no training data
```

No special flag. No separate optimization level. If a graph has associated training data, the pass fires. If not, compilation proceeds normally with zero overhead.

### Where it sits in the pipeline

Placed right after `build-prompt` (which establishes `{0}` placeholders on empty templates). DSPy needs those placeholders to exist. All subsequent passes then operate on the optimized version.

```
O1:  normalize → build-prompt → dspy-optimize → assign-priority → unconsumed-value-warning
     → scheduling → fuse-ask-ops → canonicalizer → cse → symbol-dce

O2:  normalize → build-prompt → dspy-optimize → assign-priority → prompt-canonicalization
     → template-specialization → unconsumed-value-warning → schema-narrowing → scheduling
     → fuse-ask-ops → condense-ops → dead-context-elimination → canonicalizer → cse → symbol-dce

O3:  normalize → build-prompt → dspy-optimize → assign-priority → prompt-canonicalization
     → unconsumed-value-warning → [convergence loop: template-spec → schema-narrowing
     → scheduling → fuse-ask-ops → condense-ops → DCE → canonicalizer → cse → symbol-dce] × 10
```

Subsequent passes benefit from DSPy-optimized templates:
- `template-specialization` can fold constants into the now-richer template
- `dead-context-elimination` can remove context that DSPy made redundant
- `prompt-canonicalization` can find shared prefixes across optimized templates
- `fuse-ask-ops` operates on the optimized text when merging adjacent asks
- `schema-narrowing` can narrow more precisely when the template specifies exact output fields

### How the pass works

```
  ┌──────────────────────────────────────────────────────┐
  │  C++ MLIR Pass: DspyOptimize                          │
  │  (Transforms/DspyOptimize.cpp)                         │
  │                                                        │
  │  1. Check for training data (module attr or file)      │
  │     → no training data? return immediately (no-op)     │
  │                                                        │
  │  2. Walk all AskOp / ThinkOp / ReasonOp                │
  │                                                        │
  │  3. For each op with template_str:                     │
  │     a. Compute cache key:                              │
  │        SHA256(template_str + training_data_hash        │
  │               + optimizer + model)                      │
  │     b. Check cache (<repo>/.apxm/cache/dspy/<key>.json)     │
  │                                                        │
  │     c. Cache HIT:                                      │
  │        Read optimized template from JSON                │
  │        op.setTemplateStrAttr(optimized)                 │
  │                                                        │
  │     d. Cache MISS:                                     │
  │        Write request JSON to temp file                  │
  │        llvm::sys::ExecuteAndWait("python3",             │
  │            {"-m", "apxm_dspy"},                         │
  │            Redirects={stdin=req.json, stdout=resp.json})│
  │        Read response from temp file                     │
  │        Parse with llvm::json::parse()                   │
  │        op.setTemplateStrAttr(optimized)                 │
  │        Write result to cache                            │
  │                                                        │
  │  4. Set module attr ais.dspy_optimized = N              │
  └──────────────────────────────────────────────────────┘
```

### C++ subprocess invocation

This is the first APXM C++ pass to call an external process. The mechanism uses LLVM's subprocess API (available in the conda env at `llvm/Support/Program.h`).

**Why not pipes?** `llvm::sys::ExecuteAndWait` uses **file redirects**, not pipes. stdin/stdout are redirected from/to files on disk. This is an LLVM design choice — it's portable and avoids deadlock issues with pipe buffer limits.

**The invocation pattern:**

```cpp
#include "llvm/Support/Program.h"
#include "llvm/Support/FileSystem.h"
#include "llvm/Support/JSON.h"
#include "llvm/Support/MemoryBuffer.h"

// 1. Find python3 in PATH
auto pythonOrErr = llvm::sys::findProgramByName("python3");
if (!pythonOrErr) {
    // python3 not found — emit warning, return (no-op)
    op.emitWarning("dspy-optimize: python3 not found, skipping");
    return;
}
std::string python = *pythonOrErr;

// 2. Write request JSON to temp file
llvm::SmallString<128> requestPath, responsePath;
llvm::sys::fs::createTemporaryFile("dspy-req", "json", requestPath);
llvm::sys::fs::createTemporaryFile("dspy-resp", "json", responsePath);
{
    std::error_code EC;
    llvm::raw_fd_ostream reqFile(requestPath, EC);
    // ... write request JSON ...
}

// 3. Set up file redirects: stdin=requestPath, stdout=responsePath
std::optional<llvm::StringRef> redirects[] = {
    llvm::StringRef(requestPath),   // stdin  ← read request from this file
    llvm::StringRef(responsePath),  // stdout → write response to this file
    std::nullopt                    // stderr → inherit (shows DSPy progress)
};

// 4. Build args and execute
llvm::SmallVector<llvm::StringRef> args = {python, "-m", "apxm_dspy"};
std::string errMsg;
int rc = llvm::sys::ExecuteAndWait(
    python, args,
    /*Env=*/std::nullopt,
    redirects,
    /*SecondsToWait=*/300,  // 5 min timeout (DSPy optimization takes time)
    /*MemoryLimit=*/0,
    &errMsg
);

// 5. Check result
if (rc != 0) {
    // rc == -1: execution failed (errMsg has details)
    // rc == -2: crashed or timed out
    // rc > 0:  Python exited with error code
    op.emitWarning("dspy-optimize: subprocess failed: " + errMsg);
    // Clean up temp files, skip this op (graceful degradation)
    return;
}

// 6. Read response from temp file
auto bufOrErr = llvm::MemoryBuffer::getFile(responsePath);
if (!bufOrErr) { /* handle error */ }
auto responseJson = llvm::json::parse((*bufOrErr)->getBuffer());
if (!responseJson) { /* handle parse error */ }

// 7. Extract optimized template
auto *obj = responseJson->getAsObject();
auto status = obj->getString("status");
if (status && *status == "ok") {
    auto optimized = obj->getString("optimized_template");
    op.setTemplateStrAttr(builder.getStringAttr(*optimized));
    // ... also read metric_score, trials, etc. for cache ...
}

// 8. Clean up temp files
llvm::sys::fs::remove(requestPath);
llvm::sys::fs::remove(responsePath);
```

**Key design decisions:**

- **Stderr inherits** — DSPy prints progress bars and trial results to stderr. The user sees this during compilation, which is good UX for a 3-minute operation.
- **5-minute timeout** — MIPROv2 with `auto="light"` typically finishes in 1-3 minutes. 5 minutes covers edge cases. Timeout returns rc=-2, the pass skips the op gracefully.
- **Graceful degradation** — if python3 isn't found, DSPy isn't installed, or the subprocess fails, the pass emits a warning and continues. The graph compiles with original (unoptimized) templates. Never a hard error.
- **One subprocess per module** — batch all ops into a single request to avoid subprocess overhead. The Python side processes all templates in one invocation.
- **Temp files cleaned up** — even on error paths, temp files are removed (RAII or explicit cleanup).

### Cache scope and location

The DSPy cache is **project-scoped and content-addressed**, stored at:

```
<repo>/.apxm/cache/dspy/<sha256>.json
```

Uses `ApxmPaths::cache_dir()` (from `crates/core/apxm-core/src/paths.rs`) for discovery — same resolution as MemoCache and other project caches. The project `.apxm/` directory is found by walking up from `cwd`.

**Why project-scoped (not global `~/.apxm/dspy-cache/`):**

APXM has two cache scoping models:

| Cache | Scope | Location |
|-------|-------|----------|
| Compilation artifacts | Global | `~/.cache/apxm/artifacts/<hash>.apxmobj` |
| MemoCache L2 | **Project** | `<repo>/.apxm/cache/cache.db` |
| PGO profiles | **Per-workflow** | User-provided path |
| Sessions | Per-execution | `<repo>/.apxm/sessions/<id>/` |
| **DSPy cache** | **Project** | `<repo>/.apxm/cache/dspy/<hash>.json` |

DSPy optimization is most like PGO profiles — compile-time data derived from workflow-specific training examples. Keeping it project-scoped means:

1. **Training data and cache live together** — training data is in the repo, cache is in `<repo>/.apxm/`
2. **Team sharing** — commit `.apxm/cache/dspy/` to git. Teammates get pre-optimized templates without running DSPy themselves (like `Cargo.lock`)
3. **No cross-project contamination** — different projects with different training data can't interfere
4. **`APXM_NO_CACHE=1`** disables (same env var as artifact cache)

**Why NOT per-session:** DSPy optimization is compile-time. Templates are baked into the `.apxmobj` artifact — the runtime interpolates `{0}` placeholders but never modifies the template text itself. Once compiled, the optimized template is fixed for all sessions that run that artifact. Re-optimizing per-session would mean recompiling, which defeats the purpose of having a compiled artifact.

```
compile (DSPy runs here)          execute (template is fixed)
    ↓                                 ↓
 .apxm → [dspy-optimize] → .apxmobj → session 1 (uses baked template)
                                     → session 2 (uses same template)
                                     → session N (uses same template)
```

**Why NOT per-workflow-file:** Content-addressed keys already handle deduplication. If two workflows share the same template + training data + model, they share one cache entry automatically.

### Future: session data feeding back into DSPy

Each session produces execution results (`results.json`, `metrics.json`, `node_statuses.json`). These contain actual input/output pairs that could serve as **additional training data** for DSPy re-optimization on the next compile.

```
Session 1 → results.json → accumulated training data
Session 2 → results.json → accumulated training data
  ...
apxm compile flow.apxm -O2  → dspy-optimize sees MORE training data → better templates
```

DSPy supports this via incremental optimizers (SIMBA, GEPA). This is a future enhancement — for v1, training data is user-provided and the cache is a one-time compile artifact. The project-scoped cache location (`<repo>/.apxm/cache/dspy/`) naturally supports this feedback loop: accumulated session data and DSPy cache live in the same project directory.

### Concurrency

Multiple nodes in the same graph need DSPy optimization simultaneously. The pass handles this with **one subprocess per compilation**:

```
apxm compile flow.apxm -O2
  └─ dspy-optimize pass walks all ops
     └─ collects all cache-miss templates
        └─ ONE subprocess: python3 -m apxm_dspy
           └─ receives all templates in one JSON request
              └─ runs DSPy for each template sequentially
                 └─ returns all results in one JSON response
```

No per-node subprocess overhead. No concurrent writes to the cache. The C++ pass writes cache files sequentially after the subprocess returns.

For **parallel compilations** (e.g., CI building multiple workflows simultaneously): content-addressed writes are idempotent — if two processes write the same key, they write the same content. Last writer wins. No file locking needed.

### First compile vs subsequent compiles

First compilation with training data is slow (DSPy runs LLM trials). Subsequent compilations are fast (cache hit — pure file read).

```bash
$ apxm compile flow.apxm -O2        # first time with training data: ~3 min per template
$ apxm compile flow.apxm -O2        # second time: ~0.5s (cache hit)
$ apxm compile flow.apxm -O2        # no training data at all: ~0.5s (no-op)
```

Cache invalidation:
- Change the `template_str` → cache miss, re-optimizes
- Change training data → cache miss, re-optimizes
- Change model → cache miss, re-optimizes
- Change optimizer → cache miss, re-optimizes

### Training data: where it comes from

Three sources, checked in order:

**1. Graph metadata** (inline in `.apxm` file):
```json
{
  "name": "code-review",
  "nodes": [...],
  "edges": [...],
  "metadata": {
    "dspy": {
      "training_data": "training/review.json",
      "optimizer": "mipro",
      "auto": "light",
      "metric": "llm_judge"
    }
  }
}
```

**2. Companion file** (convention: `<name>.training.json` next to `<name>.apxm`):
```
flows/
├── review.apxm
└── review.training.json     ← auto-discovered by naming convention
```

**3. Per-node attribute** (for per-template optimization):
```json
{
  "id": 1, "name": "triage", "op": "ASK",
  "attributes": {
    "template_str": "Classify this ticket: {0}",
    "training_data": "training/triage_examples.json"
  }
}
```

No source found → pass returns immediately. No error. No warning. This is the default case — most graphs won't have training data.

### Training data format

```json
[
  {
    "inputs": {"context_0": "def foo():\n  return 1+1"},
    "output": "The function foo returns the integer 2. No bugs found."
  },
  {
    "inputs": {"context_0": "import os; os.system(input())"},
    "output": "Critical: command injection via os.system()."
  }
]
```

`inputs` keys map to `{N}` placeholders: `context_0` → `{0}`, `context_1` → `{1}`.

Optional `metric` field in graph metadata specifies the quality function:
- `token_overlap` — F1 token overlap between output and expected
- `contains` — expected output is substring of actual
- `exact_match` — string equality
- `llm_judge` — LLM grades the output (most accurate, costs more)
- Default: `token_overlap`

## Backend Mapping: APXM → DSPy

DSPy uses LiteLLM internally. The Python subprocess maps APXM backend config to `dspy.LM()`:

```
APXM config.toml                         DSPy dspy.LM()
══════════════════                        ══════════════
protocol = "openai"                 →     "openai/{model_id}"
protocol = "anthropic"              →     "anthropic/{model_id}"
protocol = "ollama"                 →     "ollama_chat/{model_id}"
protocol = "vllm" (openai-compat)   →     "openai/{model_id}" + api_base

endpoint = "https://..."            →     api_base = "https://..."
api_key = "sk-..."                  →     api_key = "sk-..."
api_key = "env:VAR_NAME"            →     resolved from os.environ["VAR_NAME"]
headers = { "X-Key" = "val" }       →     extra_headers = {"X-Key": "val"}
```

The subprocess gets the backend config from `apxm backend list --json` or by reading `~/.apxm/config.toml` directly. Examples:

**Cloud OpenAI backend:**
```python
# APXM: protocol=openai, api_key=env:OPENAI_API_KEY
lm = dspy.LM("openai/gpt-4o-mini", api_key=os.environ["OPENAI_API_KEY"])
```

**Cloud Anthropic backend:**
```python
# APXM: protocol=anthropic, api_key=env:ANTHROPIC_API_KEY
lm = dspy.LM("anthropic/claude-sonnet-4-5-20250929", api_key=os.environ["ANTHROPIC_API_KEY"])
```

**On-prem vLLM backend:**
```python
# APXM: protocol=vllm, endpoint=http://gpu-server:8000/v1
lm = dspy.LM("openai/meta-llama/Llama-3-70B",
             api_base="http://gpu-server:8000/v1",
             api_key="")  # vLLM doesn't require auth
```

**Local Ollama backend:**
```python
# APXM: protocol=ollama, endpoint=http://localhost:11434
lm = dspy.LM("ollama_chat/llama3.2",
             api_base="http://localhost:11434",
             api_key="")
```

**OpenAI-compatible gateway with custom headers:**
```python
# APXM: protocol=openai, endpoint=https://gateway.corp.com/api, headers={...}
lm = dspy.LM("openai/claude-sonnet-4-5-20250929",
             api_base="https://gateway.corp.com/api",
             api_key="token",
             extra_headers={"X-Subscription-Key": "abc123"})
```

### 5. Python DSPy code (inside `apxm_dspy`)

```python
import dspy
import json
import sys

request = json.load(sys.stdin)

# 1. Map APXM backend → dspy.LM
protocol_map = {
    "openai": "openai",
    "anthropic": "anthropic",
    "ollama": "ollama_chat",
    "vllm": "openai",
}
backend = request["backend"]
prefix = protocol_map[backend["protocol"]]
lm = dspy.LM(
    f"{prefix}/{backend['model']}",
    api_base=backend.get("endpoint"),
    api_key=backend.get("api_key", ""),
    extra_headers=backend.get("headers", {}),
)
dspy.configure(lm=lm)

# 2. Build DSPy signature from template placeholders
#    template_str has {0} → maps to context_0 input field
classify = dspy.Predict("context_0 -> classification")

# 3. Load training examples as dspy.Example objects
examples = [
    dspy.Example(
        context_0=ex["inputs"]["context_0"],
        classification=ex["output"],
    ).with_inputs("context_0")
    for ex in request["training_data"]
]

# 4. Build metric function
def exact_match(gold, pred, trace=None):
    return gold.classification.strip() == pred.classification.strip()

# 5. Run optimizer (MIPROv2, instruction-only, zero few-shot demos)
optimizer = dspy.MIPROv2(metric=exact_match, auto=request.get("auto", "light"))
compiled = optimizer.compile(
    classify,
    trainset=examples,
    max_bootstrapped_demos=0,
    max_labeled_demos=0,
)

# 6. Extract optimized instruction
optimized_instruction = compiled.signature.instructions

# 7. Reconstruct template_str with optimized instructions
#    Keep the original {0} placeholder structure intact
#    Replace the instruction portion, preserve the classification format
original = request["template_str"]
# The optimized instruction wraps around the {0} context
optimized_template = (
    f"{optimized_instruction}\n\n"
    f"Classify this support ticket:\n"
    f"- Priority: [LOW/MEDIUM/HIGH/URGENT]\n"
    f"- Category: [BILLING/TECHNICAL/FEATURE_REQUEST/BUG]\n"
    f"- Sentiment: [POSITIVE/NEUTRAL/FRUSTRATED/ANGRY]\n\n"
    f"Respond in exactly 3 lines.\n\n"
    f"{{0}}"
)

# 8. Return result
json.dump({
    "status": "ok",
    "optimized_template": optimized_template,
    "original_instructions": "Classify this support ticket...",
    "optimized_instructions": optimized_instruction,
    "metric_score": 0.92,
    "optimizer": "MIPROv2",
    "trials": 10,
}, sys.stdout)
```

### 6. What DSPy discovers (example optimized instruction)

MIPROv2 might produce something like:

```
You are a customer support triage specialist. Read the ticket carefully and classify
it along exactly three dimensions.

For Priority: consider business impact (revenue, SLA, user count affected) and time
sensitivity (explicit deadlines, blocking language like "urgent", "ASAP", "can't work").
URGENT = immediate business impact + explicit time pressure. HIGH = significant impact
but no hard deadline. MEDIUM = inconvenience, has workaround. LOW = nice-to-have, no
business impact.

For Category: BILLING = payment, invoice, charge, refund, plan change. TECHNICAL =
login, access, permissions, integration, API. BUG = something worked before and now
doesn't, error codes, regressions. FEATURE_REQUEST = "would be nice", "can you add",
suggestions.

For Sentiment: assess from word choice. ANGRY = threatening, demanding, caps.
FRUSTRATED = "please help", "still can't", repeated attempts. NEUTRAL = factual,
no emotional language. POSITIVE = praise, "love your product", compliments.

Respond in exactly 3 lines, one per dimension.
```

// ─── BEFORE dspy-optimize ───────────────────────────────────────

%triage = ais.ask {

// ─── AFTER dspy-optimize ────────────────────────────────────────

%triage = ais.ask {

Key changes:
- The inline ticket text is moved to `{0}` — DSPy recognized it should be a variable input, not hardcoded
- Rich, structured instructions replace the terse original
- `ais.dspy_optimized` marker for diagnostics
- `ais.dspy_metric_score` records the quality score achieved during optimization

### 9. What subsequent passes do with the optimized template

**prompt-canonicalization** (O2+): If multiple nodes got DSPy-optimized with similar preambles (e.g., "You are a customer support..." appears in both `triage` and `customer_response`), the pass extracts the shared prefix and marks both for vLLM prefix cache reuse:

```mlir
%triage = ais.ask {
    template_str = "You are a customer support triage specialist...\n\n{0}",
    ais.shared_prefix_group = "support_specialist",
    ais.shared_prefix_est_tokens = 180
} ...
```

**template-specialization** (O2+): If `{0}` references a compile-time constant (e.g., a `CONST_STR` node), the constant gets folded into the optimized template, producing an even richer final prompt.

**dead-context-elimination** (O2+): If DSPy's optimized instruction made some context operands redundant (e.g., the instruction now contains what used to be a separate context input), DCE removes the unused operands and renumbers placeholders.

## Dependencies

### How DSPy gets installed

DSPy is an **optional** Python dependency. APXM follows its existing pattern for optional components (same as vLLM):

**1. `.dekk.toml` install component** — user installs with `dekk apxm install --with dspy`:

```toml
# .dekk.toml
[[install.components]]
name = "dspy"
label = "DSPy Prompt Optimizer"
description = "Automatic prompt optimization via DSPy (Stanford NLP)"
run = "pip install dspy-ai>=2.6.0"
default = false
requires = ["pip"]
```

This follows the exact same pattern as the existing vLLM component:
```toml
[[install.components]]
name = "vllm"
label = "vLLM (graph-aware fork)"
run = "git submodule update --init external/vllm && pip install -e external/vllm"
default = false
requires = ["pip"]
```

**2. `tools/scripts/deps.py`** — `apxm doctor` checks for DSPy availability:

```python
# Added to APXM_DEPENDENCIES list
_dep(
    name="DSPy",
    command="python3",
    version_pattern=r"(\d+\.\d+\.\d+)",  # via python3 -c "import dspy; print(dspy.__version__)"
    version_constraint=">=2.6",
    required=False,  # optional — same as Ninja, LLVM
),
```

When the user runs `apxm doctor`, DSPy shows as optional (not required). Missing DSPy is informational, not a failure.

**3. Python module at `tools/apxm_dspy/`** — the subprocess entry point:

```python
# tools/apxm_dspy/__main__.py
try:
    import dspy
except ImportError:
    import json, sys
    json.dump({"status": "error", "error": "dspy-ai not installed. Run: pip install dspy-ai>=2.6.0"}, sys.stdout)
    sys.exit(1)
# ... proceed with optimization ...
```

The C++ pass handles this gracefully: if `python3 -m apxm_dspy` exits with error, it emits a warning and continues with unoptimized templates.

### Dependency summary

| Layer | What | Required? |
|-------|------|-----------|
| **Conda** (`.dekk/environment.yaml`) | No changes — DSPy is pip, not conda | — |
| **pip** (`dspy-ai>=2.6.0`) | Installed via `dekk apxm install --with dspy` | Optional |
| **dekk** (`.dekk.toml`) | New `[[install.components]]` entry | — |

## Comparison with Removed Frontend Approach

| Aspect | Old (Removed) | New (Compiler Pass) |
|--------|---------------|---------------------|
| Location | `apxm-frontend/python/` | `Transforms/DspyOptimize.cpp` + `tools/apxm_dspy/` |
| When it runs | Graph construction time | During MLIR pass pipeline, O1+ |
| Trigger | Manual Python API call | Automatic — fires when training data exists |
| Placeholder syntax | `{{name}}` (Jinja, wrong) | `{N}` (positional, matches runtime) |
| Output attribute | `__dspy_optimized_template` (unread) | `template_str` (the real attribute) |
| Caching | None (re-ran every time) | SHA256-keyed cache in `<repo>/.apxm/cache/dspy/` |
| Graph awareness | Operated on Python dict | Full MLIR IR context |
| Subsequent passes | None (end of pipeline) | template-spec, DCE, prompt-canon all run after |
| Backend resolution | Hardcoded | Maps from APXM `config.toml` backends |
