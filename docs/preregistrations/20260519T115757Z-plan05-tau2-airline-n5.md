## Workload and rationale

- Benchmark: `tau2-bench` (vendored at `tools/external/tau2-bench/`, pinned
  SHA `0ed8c0ef0a1f6b024a0fb733e186922411874879` — see
  `tools/external/tau2-bench/external-pins.txt`).
- Domain: `airline` (50-task suite; the canonical task-quality domain in
  the τ²-bench paper; multi-step tool calls with retry semantics).
- Sub-sample: first **N=5** tasks per arm by `tau2`'s default ordering, both
  arms run with identical `--seed` so the same 5 tasks land in each arm.
- One trial per task (`--num-trials 1`). The pair is therefore 5 paired
  observations on a binary (pass / fail) outcome.
- Why airline (not mock): mock is a 5-tool sandbox with trivial pass
  criteria — it cannot move pass@1 in either direction and would not
  falsify the dispatch hypothesis. Airline exercises real multi-step
  policy compliance (booking / modify / cancel / refund rules) against a
  domain-specific tool schema, which is the regime Plan 05 EVAL has to
  speak to.
- Why N=5 (not larger): N=5 is the methodology charter's minimum cell
  size (Plan 00 §2). The Slurm wall budget on the live `vllm-gptoss`
  permits a larger N, but this run is the **first** claim-bearing Plan
  05 cell — its purpose is to establish the wire-up and produce a
  defensible per-arm pass@1 with a wide-but-honest confidence band, not
  to chase a statistically powered claim. A follow-up N=20+ run is
  pre-flagged in the Plan 05 roadmap, gated on this one shipping.

## Hypothesis under test

- Form: At N=5 airline tasks with the same seed in both arms, APXM-on
  (HAL adapter injecting `vllm_xargs.apxm` per request) **does not
  degrade** task `pass_at_1` vs flat-http (HAL adapter stripping any
  `vllm_xargs.apxm`) on `gpt-oss-120b` running on `vllm-gptoss`. Both
  arms hit the **same** vLLM binary (same image, same
  `--enable-prefix-caching`, same `--scheduling-policy priority`,
  `mwon-postrebase-ray` middleware overlay) through the **same** HAL
  adapter binary — the only on-the-wire difference is whether the
  request body carries an `extra_body.vllm_xargs.apxm` block.
- Concrete value: the paired difference (apxm-on `pass_at_1` − flat-http
  `pass_at_1`) at N=5 must lie inside the practical-equivalence interval
  **[−0.20, +0.20]**. Anything outside that interval is a real signal
  worth investigating (a regression on the apxm-on side would imply
  the apxm dispatch path harms task quality; a large positive would
  motivate a follow-up powered run).
- This is an **equivalence-style hypothesis**, not a superiority claim.
  Plan 05's first deliverable is "APXM does not break task quality";
  superiority requires a much larger N and is explicitly out of scope
  for this run.

## Metric tier

- Primary metric: `pass_at_1` per arm at N=5, plus the **paired
  difference** apxm-on − flat-http on identical task IDs (same seed →
  same task subset). Source: `simulations[i].reward_info.reward` from
  each arm's `results.json`.
- Secondary metrics (reported but not claim-bearing):
  - `mean_steps` (number of agent turns per task)
  - `mean_tool_calls` (count of tool-call messages per task)
  - `mean_duration_s` (wall time per simulation)
  - `db_match_rate` (fraction of tasks where `reward_info.db_check.db_match`)
  - `termination_reasons` (count by reason)
- Decision rule: ship the claim iff (a) **both arms run to completion
  with zero agent errors and zero tau2 system errors**, AND (b) the
  paired pass-at-1 difference lies inside [−0.20, +0.20]. Otherwise,
  the run becomes a recorded honest-null (or honest-negative if
  apxm-on degraded) and the claim file frames it accordingly.
- Honest negatives: any task where the two arms diverge on pass@1 must
  be cited per-task in the claim file (with the task ID and the
  terminating condition on each arm).

## Pin-engagement gate

- **Not load-bearing for this claim.** tau2-bench airline tasks are
  short-prefix conversational requests; the apxm-on arm injects a
  `graph_id` + `reuse_group` + `priority_class` per request, but the
  dispatch outcome (pin engagement, prefix-cache hit) is a Plan 04-class
  measurement, not a Plan 05 task-quality measurement. The
  apxm-on response headers (`x-apxm-fields-honored`) will be captured
  via HAL adapter pass-through and recorded in the run manifest, but
  pin-engagement is **not** required for this claim to ship.
- If `x-apxm-fields-honored` is absent on apxm-on responses, that is a
  manifest-recorded honest negative — the apxm-on arm degenerates to
  flat-http on the wire and the pass-at-1 hypothesis becomes
  uninformative for that run (rerun required).

## Matrix design

Single workload, paired arms over identical N=5 airline tasks:

| Arm | Model | HAL adapter args | Wire shape |
|---|---|---|---|
| `apxm-on` | gpt-oss-120b | `--backend apxm-on --inject-apxm --graph-context tau2-airline-n5` | `extra_body.vllm_xargs.apxm` block injected per request |
| `flat-http` | gpt-oss-120b | `--backend flat-http` | apxm block (if any) stripped per request |

Both arms target the same `vllm-gptoss` service (job 54322, port 8916,
host a04u07). HAL adapter runs on the same node as the vLLM service via
`dekk apxm vllm service-exec`. Each arm has its own HAL adapter port
(`18080` for apxm-on, `18081` for flat-http) launched serially — same
process binary, different CLI args.

tau2 runner config (identical across arms):

```
tau2 run \
  --domain airline \
  --agent-llm openai/gpt-oss-120b \
  --user-llm openai/gpt-oss-120b \
  --num-trials 1 \
  --num-tasks 5 \
  --seed 300 \
  --save-to .apxm/evaluation/agentic/<TS>-airline-n5/<arm>/results.json
```

## Honest-negative discipline

Per Plan 00 §6 and [`.apxm/docs/claims/CLAIMS-INDEX.md`](../../.apxm/docs/claims/CLAIMS-INDEX.md):

- If apxm-on pass-at-1 is **lower** than flat-http by more than 0.20,
  ship the claim file as an **honest negative** (APXM dispatch degrades
  task quality on airline; cite per-task failures + termination
  reasons; do not silently omit).
- If `x-apxm-fields-honored` is absent on apxm-on responses, ship the
  artifact as a wire-up null (not claim-bearing) and rerun.
- Any agent crash / tau2 system error during the run invalidates the
  cell; the partial result is preserved on disk for audit (per the
  `mooncake-replay-partial.md` pattern) but no claim is drawn.
- N=5 is acknowledged as small; the claim file must state the
  equivalence-band-only nature of the conclusion and pre-flag the
  N=20+ follow-up.
