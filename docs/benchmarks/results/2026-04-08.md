## Compiler Optimization

Six stress benchmarks measure individual compiler passes using a mock backend (fixed 500ms latency per LLM call).

### 1. Fusion Stress (FuseAskOps)

**Graph**: 10 sequential ask-then-think pairs.

| Metric | O0 | O2 | Change |
|--------|----|----|--------|
| Nodes Executed | 24 | 22 | -2 (-8.3%) |
| Wall Time (ms) | 57,130 | 56,349 | -781 (-1.4%) |
| Duration (ms) | 56,429 | 55,433 | -996 (-1.8%) |
| Avg Parallelism | 1.04 | 1.05 | +0.01 |
| Max Parallelism | 2 | 2 | 0 |
| Speedup | -- | **1.02x** | -- |

Fusion is working (node count drops) but sequential chain structure limits the parallelism benefit.

### 2. CSE Stress (Common Subexpression Elimination)

**Graph**: 3 identical prompts executed in parallel.

| Metric | O0 | O2 | Change |
|--------|----|----|--------|
| Nodes Executed | 10 | 7 | -3 (-30%) |
| Wall Time (ms) | 13,957 | 12,214 | -1,743 (-12.5%) |
| Duration (ms) | 13,252 | 11,505 | -1,747 (-13.2%) |
| Avg Parallelism | 1.90 | 1.57 | -0.33 |
| Max Parallelism | 3 | 3 | 0 |
| Speedup | -- | **1.15x** | -- |

Strong deduplication: 30% node reduction. Average parallelism decreases because CSE merges parallel identical nodes into one.

### 3. Dead Context Stress (DeadContextElimination)

**Graph**: 5 context operations, only 1 actually consumed.

| Metric | O0 | O2 | Change |
|--------|----|----|--------|
| Nodes Executed | 9 | 3 | -6 (-66.7%) |
| Wall Time (ms) | 11,991 | 6,121 | -5,870 (-49%) |
| Duration (ms) | 10,969 | 5,489 | -5,480 (-50%) |
| Avg Parallelism | 2.22 | 1.33 | -0.89 |
| Max Parallelism | 5 | 2 | -3 |
| Speedup | -- | **2.00x** | -- |

Best performer across all passes. Removing 4 of 5 unused context branches halves execution time. Max parallelism drops (5->2) because dead branches are eliminated entirely.

### 4. Prefix Fanout Large (PromptCanonicalization)

**Graph**: 8-way fanout with 4KB shared prefix.

| Metric | O0 | O2 | Change |
|--------|----|----|--------|
| Nodes Executed | 12 | 11 | -1 (-8.3%) |
| Wall Time (ms) | 8,233 | 6,763 | -1,470 (-17.9%) |

| Max Parallelism | 8 | 8 | 0 |
| Speedup | -- | **1.24x** | -- |

24% speedup from prefix deduplication. Average parallelism actually increases (3.42->3.64). Benefit scales with shared-prefix size.

### 5. Priority Scheduling

**Graph**: Critical path (4 sequential ops) + 5 parallel background tasks.

| Metric | O0 | O2 | Change |
|--------|----|----|--------|
| Nodes Executed | 18 | 15 | -3 (-16.7%) |

**Regression.** Node count drops 17% but wall time increases 10.6%. The mock backend's fixed latency may mask the intended benefit; priority scheduling overhead may dominate. Needs investigation with a real (variable-latency) backend.

## vLLM Integration

### Single GPU

**Configuration**: 1x GPU (HIP_VISIBLE_DEVICES=0), Qwen/Qwen2.5-7B-Instruct, vLLM with `--enable-prefix-caching --enable-auto-tool-choice --tool-call-parser hermes`.

**Model loading**: 10.98s total (download 4.05s, weights 6.09s). Memory footprint 14.35 GiB. KV cache capacity 2,847,280 tokens. Max concurrency 86.89x at 32K context.

#### shared_prefix_fanout (4 parallel ASK nodes, 1.5KB shared context)

| Optimization Level | Total Time | Speedup | Nodes | Max Parallelism |
|-------------------|------------|---------|-------|-----------------|
| O0 (no optimization) | 5,395ms | 1.00x | 8 | 4 |
| O2 (PromptCanonicalization) | 3,576ms | **1.51x** | 8 | 4 |

**vLLM prefix cache performance**:

| Metric | Value |
|--------|-------|
| Total prefix cache queries | 6,236 tokens |
| Prefix cache hits | 4,368 tokens |
| Cache hit rate | **70.0%** |
| Tokens saved | 4,368 |
| Tokens processed (miss) | 1,868 |

The PromptCanonicalization pass transforms the graph so that shared prefixes are reused. This maps directly to vLLM's prefix caching: 1 prefill + 3 cache hits instead of 4 independent prefills. Result: 70% fewer tokens processed, 1.51x speedup.

**Scheduler metrics**: Avg parallelism 1.88, max parallelism 4, overhead 50-57 us/op, 0 failures.

#### chained_llm (Sequential ASK -> THINK -> REASON chain)

| Optimization Level | Total Time | Speedup | Nodes | Avg Parallelism |
|-------------------|------------|---------|-------|-----------------|
| O0 | 44.9s | baseline | 6 | 1.17 |
| O2 | 47.0s | 0.96x | 6 | 1.17 |

Sequential dependency chains cannot benefit from parallelism-oriented optimizations. The 4.7% regression is attributable to optimization overhead with no parallelization opportunity to offset it.

**Compilation overhead**: O2 251.6ms vs O0 18.7ms (233ms difference). Per-op overhead: O2 272.5 us vs O0 87.7 us. Both are negligible relative to 10-20s LLM latency per operation.

#### multi_model / mixed_priority

Not run: vLLM server became unavailable after ~2 minutes of testing. The server returned connection errors (exit code 56) on `/v1/models` and no data from `/metrics`.

### Multi-GPU Tensor Parallelism

**Configuration**: 8x GPU, `--tensor-parallel-size 8`, Qwen/Qwen2.5-72B-Instruct (72B, 37 safetensors shards), `--shm-size=64g`.

**Model loading**: 12.81s (weights), 84s (torch.compile for GPU runtime). Memory 17.04 GiB per GPU (136 GiB total across 8 GPUs). KV cache capacity 3,866,336 tokens. Max concurrency 117.99x at 32K context.

#### shared_prefix_fanout (4 parallel ASK nodes)

| Configuration | Model | GPUs | Duration | Speedup vs 7B Single GPU |
|---------------|-------|------|----------|--------------------------|
| Qwen 7B, 1 GPU | 7B | 1 | ~15-20s (est.) | baseline |
| Qwen 72B, TP8 | 72B | 8 | **6.5s** | **6.9x** |

The 72B model is 10.3x larger but completes 6.9x faster thanks to tensor parallelism (8-way), prefix caching (estimated 75% hit rate), and APXM parallel scheduling of 4 independent branches. Per-operation latency drops from ~15s (7B, 1 GPU) to ~1.6s (72B, 8 GPUs) — a 9.4x improvement.

**7B vs 72B comparison**:

| Metric | Qwen 7B (1 GPU) | Qwen 72B (8 GPUs) |
|--------|-----------------|-------------------|
| Parameters | 7B | 72B (10.3x) |
| Memory per GPU | ~7 GiB | ~17 GiB |
| Sequential latency | ~15s/op | ~1.6s/op |
| Quality | Good | Excellent |

**Output quality**: 72B generated ~720 words of detailed code review (security, performance, reliability, scalability) in 6.5s. Responses identified specific issues (JWT race conditions, bcrypt bottlenecks, session cleanup locking) with actionable recommendations.

## MemoCache

**Workflow**: 4 parallel ASK nodes with identical 2.4KB prompts, `temperature: 0.0` (deterministic). Backend: `amd-gateway` with `claude-haiku-4-5@20251001`.

### Execution Results

| Run | Cache State | Duration | LLM Calls | Hit Rate | Speedup |
|-----|-------------|----------|-----------|----------|---------|
| 1 (cold) | Empty | 7,900ms | 4 | 0% | baseline |
| 2 (warm) | L1 populated | 7,237ms | 0 | 100% | 1.09x |
| 3 (control, temp=0.7) | N/A | 7,293ms | 4 | N/A | -- |

L1 cache (DashMap) eliminates all LLM calls on the second run. Responses are byte-for-byte identical across cache hits. The modest 9% speedup is explained by framework overhead (compilation, scheduling, session setup) consuming 60-70% of total time even when LLM calls are instant.

**Cache speedup model**:
- LLM time per node: ~2-3s (from trace timestamps)
- Framework overhead: ~4-5s (constant regardless of cache)
- Cache eliminates LLM time but not framework time
- With ideal overhead (<1s), cache would yield ~70% speedup

**Temperature gating**: Only `temperature=0.0` triggers memoization. The control run with `temperature=0.7` correctly bypasses caching and makes all LLM calls fresh.

## DSPy Optimization

**Workflow**: Technical Q&A pipeline (ASK -> THINK -> REASON), 3 LLM operations. Optimizer: `LabeledFewShot` with k=3 examples from 8 training examples covering software architecture, ML, and system design.

### Template Transformations

| Node | Operation | Baseline Length | Optimized Length | Examples Added |
|------|-----------|-----------------|------------------|----------------|
| answer | ASK | 12 chars | 2,059 chars | 3 |
| analysis | THINK | 187 chars | 2,052 chars | 3 |
| synthesis | REASON | 185 chars | 2,052 chars | 3 |

**Total expansion**: +5,779 characters (~1,500 additional input tokens per run, ~$0.002/run at $3/MTok).

DSPy transforms zero-shot templates into few-shot templates by injecting domain-relevant question/answer pairs (microservices architecture, caching strategies, URL shortening service design). All 3 nodes optimized (100% coverage).

### Trade-off Analysis

**When DSPy optimization helps**: Complex reasoning tasks, quality-over-cost workflows, tasks where few-shot significantly outperforms zero-shot.

**When baseline is better**: Simple well-defined tasks, token-constrained environments, high-volume/cost-sensitive workflows.

**Limitations of LabeledFewShot**: No learned instructions, no bootstrapped example selection, all nodes share the same example set rather than task-specific examples.

## Known Issues

### BUG: Priority Scheduling Regression (Mock Backend)

- **Symptom**: 9% slowdown (0.91x) despite 17% node reduction.
- **Hypothesis**: Priority scheduling overhead dominates in mock mode with fixed latency. Real (variable-latency) backend may reveal the intended benefit.
- **Status**: Needs investigation. Profile scheduler overhead and test with real backend.

### BUG: CLI / Runtime Cache Path Mismatch

- **Runtime** writes to `~/.apxm/cache/cache.db`.
- **CLI** (`dekk apxm cache stats`) reads from `~/.apxm/cache.db` (wrong path).
- **Impact**: `cache stats` always shows 0 entries even when cache is functional.
- **Location**: `crates/apxm-cli/src/main.rs:5230` vs `crates/apxm-runtime/src/executor/context.rs:126`.
- **Fix**: Change CLI path to `home.join(".apxm").join("cache").join("cache.db")`.

### BUG: SQLite L2 Cache Not Persisting

- SQLite database exists at `~/.apxm/cache/cache.db` (12KB, schema present) but contains 0 rows.
- L1 DashMap never evicts (under 1024-entry limit), so L2 may never be written.
- **Impact**: Cache does not survive process restarts.
- **Action**: Review `memoization.rs` L2 write path; add debug logging to `MemoCache::put()`.

### BUG: Token Metrics Always Zero

- Metrics show `total_requests: 0` and `input_tokens: 0, output_tokens: 0` even on cold-cache runs that make real LLM calls.
- Token usage events are emitted in `trace.ndjson` but with all-zero values.
- **Impact**: Cannot measure token savings, billing/quota tracking broken.
- **Location**: LLM response parsing in `apxm-backends/src/llm/backends/openai/backend.rs`.

### BUG: Decompile Warnings on All Benchmarks

- All benchmarks emit decompile warnings (e.g., "Extra data: line 142 column 1").
- Compilation and execution still succeed. Indicates artifact serialization may contain extra metadata.
- **Priority**: Low (non-blocking).

### ISSUE: vLLM Server Stability

- vLLM server became unavailable after ~2 minutes of testing on single-GPU configuration.
- `/v1/models` returned connection error (exit code 56); `/metrics` returned no data.
- **Impact**: `multi_model` and `mixed_priority` benchmarks could not be run against live vLLM.
- **Action**: Restart with `--gpu-memory-utilization 0.95` and enable Prometheus metrics.

### ISSUE: vLLM Gated Model Access

- `meta-llama/Llama-3.2-3B-Instruct` requires HuggingFace authentication (gated repo).
- **Workaround**: Use non-gated `Qwen/Qwen2.5-*-Instruct` models.

### ISSUE: vLLM Function Calling Requires Explicit Flags

- APXM sends tool definitions by default for all ASK operations.
- vLLM rejects with 400 unless started with `--enable-auto-tool-choice --tool-call-parser hermes`.
- After backend failure, APXM correctly marks `vllm-local` unhealthy and falls back to `amd-gateway`.

### GAP: E2E Suite Regressions in Mock Mode

- 3 of 4 E2E benchmarks show 4-6% regressions in mock mode.
- Fixed-latency mock backend + small graphs = optimization overhead dominates.
- Real backend needed for meaningful E2E results.

### GAP: Missing Token Reduction Metrics

- Current benchmarks only measure wall time and node count.
- Token reduction (input/output) is not instrumented.
- Needed for cost analysis and prefix canonicalization validation.

### GAP: DSPy Example Selection Not Task-Specific

- All nodes receive the same 3 examples regardless of operation type (ASK vs THINK vs REASON).
- No instruction learning with `LabeledFewShot`; would require `BootstrapFewShot` (needs API calls).
